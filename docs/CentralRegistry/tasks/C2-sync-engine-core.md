ეს არის ამოცანა C2 SupportTools-ის ცენტრალიზებული რეესტრის გეგმიდან. ჯერ წაიკითხე:

§7-ის წესები სავალდებულოა: commit, push და pull არ გააკეთო; build-ი მკაცრია; ტესტები სავალდებულოა; საიდუმლოებებს არ კითხულობ და არ ბეჭდავ.

მიზანი: სინქრონიზაციის ძრავის ბირთვი. ის 3-მხრივია (ლოკალური / სერვერის / ბოლო სინქრონიზაციის მდგომარეობა), ჩანაწერის დონეზე, `Version`-ით (G5).
- ამ ამოცანაში არ არის: UI, რეალური სერვერის გამოძახება, კონკრეტული კოლექციების mapper-ები. ესენი C3, C4 და C5-ია.
- ყველაფერი fake ადაპტერებით უნდა დაიტესტოს.
- კოდის ადგილი: `LibSupportToolsServerWork\Registry\Sync\` (ან დაასაბუთე სხვა). LibSupportToolsServerWork უკვე მიმართავს SupportToolsData-ს და სერვერის კონტრაქტებს.

სამუშაო:

1. სინქრონიზაციის მდგომარეობა. ლოკალურია და ინახება `SupportToolsParameters`-ის ახალ ველში `RegistrySyncState`, მოდელი `SupportToolsData\Models\`-ში. ასე მონაცემი და მისი მდგომარეობა ერთად, ერთი `Save`-ით ინახება.
   - შინაარსი:
     - თითო კოლექციისთვის, თითო ჩანაწერის გასაღებისთვის: სერვერის `Version` და ლოკალური კონტრაქტის ჰეში ბოლო წარმატებული სინქრონიზაციისას;
     - თითო კოლექციისთვის `ExcludedKeys`: სინქრონიზაციიდან გამორიცხული ჩანაწერები, მაგალითად Linux-ისთვის განსხვავებული DB კავშირი;
     - `LastSyncUtc`.
   - გასაღებები რეგისტრის გარეშე შედარდება (G8). Newtonsoft deserialization ჩვეულებრივ dictionary-ს ქმნის, ამიტომ ჩატვირთვისას case-insensitive ხედი ააგე, ან სხვა საიმედო გზა აირჩიე და დატესტე.

2. ადაპტერის ინტერფეისი (სახელი შენ აირჩიე). თითო კოლექციას ერთი ადაპტერი აქვს:
   - `CollectionName` და `Order`: დამოკიდებულების რიგი. მაგალითად Environments/Runtimes/… < ApiClients < DatabaseServerConnections < Servers < … < Projects.
   - `GetLocalRecords()`: გასაღები → ნორმალიზებული კონტრაქტი (კანონიკური გზებით).
   - `GetServerRecords(ct)`: გასაღები → კონტრაქტი + `Version`. აბრუნებს `Result`-ს.
   - `Upsert(key, contract, expectedVersion, ct)`: აბრუნებს `Result<int>`-ს (ახალ ვერსიას).
   - `Delete(key, expectedVersion, ct)`.
   - `ApplyLocal(key, contract)`: კონტრაქტი ლოკალურ მოდელში ერთიანდება, კომპიუტერის ველების შენარჩუნებით (კონკრეტულ ლოგიკას C3/C4 დაწერს).
   - `RemoveLocal(key)`.
   - სერვერის შეცდომების კოდები გამოიყენე: `ConcurrencyConflict`, `RecordWithNameNotFound` და სხვა. ისინი `SupportToolsServerApiClientErrors`-შია (B1); ჩაწერე, როგორ ცნობს ძრავა თითოეულს.

3. ჰეში.
   - SHA-256, კონტრაქტის დეტერმინისტული JSON-იდან.
   - `Version` ჰეშში არ შედის: გამოთვლამდე ნულდება ან გამოირიცხება.
   - სერიალიზაციის პარამეტრები ერთ ადგილას დააფიქსირე.
   - ნორმალიზაცია (`""` → null, სიმრავლეების დალაგება) mapper-ის საქმეა (C3/C4). ძრავა კი შეამოწმებს, რომ ორჯერ ნორმალიზებული კონტრაქტი იგივე ჰეშს იძლევა.

4. დამგეგმავი (planner). სუფთა ფუნქციაა: შემავალი მონაცემებია ლოკალური ჩანაწერები, სერვერის ჩანაწერები და მდგომარეობა; შედეგი არის `SyncPlan` თითო ჩანაწერზე. წესები:
   - ჩანაწერი ორივე მხარესაა და მდგომარეობაშიც არის:
     - localChanged = (ჰეში ≠ state.Hash), serverChanged = (Version ≠ state.Version);
     - არცერთი არ შეცვლილა → InSync;
     - მხოლოდ სერვერი → Pull (Update);
     - მხოლოდ ლოკალური → Push (Update);
     - ორივე → Conflict(BothChanged). გამონაკლისი: თუ შიგთავსი თანაბარია, InSync და მდგომარეობის განახლება.
   - ჩანაწერი მხოლოდ ლოკალურადაა:
     - მდგომარეობაში არის → სერვერზე წაიშალა: ლოკალური არ შეცვლილა → Pull(Delete); შეიცვალა → Conflict(DeletedOnServer);
     - მდგომარეობაში არ არის → Push(Add).
   - ჩანაწერი მხოლოდ სერვერზეა:
     - მდგომარეობაში არის → ლოკალურად წაიშალა: სერვერზე არ შეცვლილა → Push(Delete); შეიცვალა → Conflict(DeletedLocally);
     - მდგომარეობაში არ არის → Pull(Add).
   - პირველი სინქრონიზაცია (მდგომარეობა ცარიელია) და ჩანაწერი ორივე მხარესაა: თანაბარია → InSync; განსხვავდება → Conflict(FirstSyncDiffers). seed-ის დროს მომხმარებელი ირჩევს „Local wins“-ს (C5).
   - `ExcludedKeys` → Skipped.

5. შემსრულებელი (executor).
   - შემავალი მონაცემები: გეგმა და შერჩევა. შერჩევის ვარიანტები:
     - ყველა არაკონფლიქტური;
     - მხოლოდ Pull;
     - მხოლოდ Push;
     - კონფლიქტების გადაწყვეტა: Local / Server / Skip თითოზე.
   - რიგი:
     1. ჯერ სერვერის ოპერაციები: upsert-ები `Order`-ის ზრდადობით, delete-ები კლებადობით.
     2. შემდეგ ლოკალური ცვლილებები: ApplyLocal ზრდადობით, RemoveLocal კლებადობით.
     3. ბოლოს ერთი `IParametersManager.Save`, თუ რამე შეიცვალა: ლოკალური მონაცემი ან მდგომარეობა.
   - push-ის `ConcurrencyConflict` ან 404 შედეგში კონფლიქტად აღირიცხება და დანარჩენი გრძელდება.
   - ტრანსპორტის შეცდომისას (სერვერი მიუწვდომელია) სერვერის დარჩენილი ოპერაციები ჩერდება, უკვე წარმატებულები კი მდგომარეობაში აღირიცხება.
   - ყოველი წარმატებული ოპერაციის შემდეგ ჩანაწერის მდგომარეობა ახლდება: ახალი ვერსია და ჰეში.
   - ლოკალური ცვლილება იმავე მეხსიერების ობიექტში ხდება, ადგილზე: dictionary-ების ეგზემპლარები არ იცვლება, რადგან მენიუს რედაქტორები მათზე მიმართვებს ინახავს.
   - შედეგი: ანგარიში თითო ჩანაწერზე, რომელსაც C5 აჩვენებს.
