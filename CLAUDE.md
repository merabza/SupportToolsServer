## Architecture

Clean Architecture / CQRS, the same layout as `AppGanmartebaGe`. Request flow:

endpoint (`SupportToolsServer.WebApi/Endpoints/V1/*Endpoints.cs`) → command/query → `ICommandHandler`/`IQueryHandler` (`SupportToolsServer.Application/<Area>/<UseCase>/`) → repository interface (`SupportToolsServerCore.Domain`) → EF implementation (`SupportToolsServer.Infrastructure/Repositories`) over `ISupportToolsServerDbContext` → the handler commits with `IUnitOfWork.SaveChangesAsync` → `Result` → `TypedResults` / `CustomResults.Problem`.

- `SupportToolsServer.Application` — one folder per use case (`GitRepos/UpdateGitRepo/`, `GitIgnoreFileTypes/SyncUp/`, …) holding the command/query, its handler and an optional `AbstractValidator`. `AddApplication(debugLogger, typeof(SupportToolsServer.Application.AssemblyReference))` scans this assembly and decorates the handlers with validation + logging, and `AddFluentValidation` (WebSystemTools.ValidationTools) registers the validators, so a new handler or validator needs no DI code. Only **command** handlers get the validation decorator. Validators use the error codes of `SupportToolsServerApiClientErrors` (Shared repo); shared rules live in `Validation/` (`RequiredWithMaxLength`, `UniqueValues`, the git folder and address rules of `GitRules`) and the lengths come from the entity constants (`GitRepo.NameMaxLength`, …) that the EF configurations also use.
- `SupportToolsServer.Infrastructure` — EF repositories; a new repository needs an `AddScoped` in `DependencyInjection/SupportToolsServerRepositoriesDependencyInjection.cs` (`AddSupportToolsServerRepositories`). `GitProjects/` holds the server-side git clone/pull (see below), registered by `AddSupportToolsServerGitProjects`.
- `SupportToolsServer.WebApi` — minimal-API endpoint groups exposing `Use...Endpoints` extension methods, aggregated in `UseSupportToolsServerApi`. Endpoints inject `ICommandHandler<TCommand>` directly. Routes come from `SupportToolsServerApiRoutes` in the Shared repo.
- `SupportToolsServer` (host) — `Program.cs` wires `AddSupportToolsServerDatabase` (DbPart: context, `ISupportToolsServerDbContext`, `IUnitOfWork`, `IDomainEventsDispatcher`), `AddApplication`, `AddFluentValidation`, `AddSupportToolsServerRepositories` and `AddSupportToolsServerGitProjects`.

Repositories read with `AsNoTracking` and stage changes with explicit `Add`/`Update`/`Delete`; the handler commits once. Gitignore and editorconfig types are updated by passing a new instance with the stored `Id` to `Update`. A `GitRepo` is changed in place instead: the handlers call `GitRepo.Update(...)` on the loaded no-tracking instance, which raises `GitRepoUpdatedDomainEvent`, and pass that same instance to the repository's `Update` (a new repo comes from `GitRepo.Create`, which raises `GitRepoAddedDomainEvent`). Adding a table: entity (+ repository interface) in `SupportToolsServerCore.Domain`, a `DbSet` on both `ISupportToolsServerDbContext` and `SupportToolsServerDbContext`, a configuration in `SupportToolsServerDbPart.Db/Configurations`, then a migration in `SupportToolsServerDbTools`, generated where the Core and DbPart clones are current. The only migration so far is the squashed `20260929190002_Initial`, which creates all three tables.

### Server-side git clone/pull

Saving an added or updated `GitRepo` (`updategitrepo`, `uploadgitrepos`) also clones or updates that repo on the server, under `{AppOptions:WorkFolder}\Gits\`. `SupportToolsServerDbContext.SaveChangesAsync` dispatches the tracked entities' domain events after saving, through `IDomainEventsDispatcher` (`SystemTools.SharedKernel`):

`GitRepoAddedDomainEvent` / `GitRepoUpdatedDomainEvent` → `GitRepoSavedDomainEventHandler` → `UpdateGitProjectCommand` → queue (`GitProjectUpdateQueue`, a single-reader channel) → `GitProjectUpdateBackgroundService`, which runs `UpdateGitProjectCommandHandler` in its own scope, one command at a time.

The handler clones the repo (first deleting a folder that was cloned from another address), discards local changes in an existing clone, or otherwise pulls when the remote has new commits. The request does not wait for git, and git failures are only logged. The folder is the folder name with both separators replaced by `.` (the client's cache rule, `GitFolderCountHelper`), so it is always a direct subfolder of `Gits`; a folder name with the `{SpaProjectFolderRelativePath}` prefix uses the git's name instead, like the client's `GitRepos.Create` with `useGitRecordNameForComplexGitProjectFolderName`. After the validator (see the rules below), `GitsWorkFolder` is the second line of defence: it checks with `Path.GetFullPath` that the result is a subfolder of `Gits` (not `Gits` itself), otherwise it returns `FolderIsOutsideGitsFolder` and the handler neither deletes nor clones. `GitClient` passes every argument separately through `ProcessStartInfo.ArgumentList`, never as one interpolated string, and clones with `git clone -- <address> <path>`. `AddApplication` finds the domain-event handler like the command handlers; `AddSupportToolsServerGitProjects` registers the rest (`AppOptions`, the queue, the hosted service, `IGitsWorkFolder`, `IGitClient`). `AppOptions:WorkFolder` is required: it is validated with `ValidateOnStart`, so the host does not start without it (`appsettings.json` holds the relative default `WorkFolder`).

### Git folder and address rules

`GitRepoModelValidator` (so both `updategitrepo` and `uploadgitrepos`) checks the two values with `Validation/GitRules`; the error codes are `InvalidGitFolderName` and `InvalidGitAddress` (Shared repo).

- **Folder name**: a relative path of one or more segments separated by `\` or `/`. A segment is not empty, contains none of `< > : " | ? *` and no control characters (a fixed set, not `Path.GetInvalidFileNameChars()`, so the result does not depend on the OS), and does not end with `.` or a space. That also rules out `.`, `..`, the names Windows trims to them (`...`, `.. `) and rooted paths (`C:`, `\\server`, `/x`). A leading `{SpaProjectFolderRelativePath}` (the client's `GitDataModel.SpaProjectFolderRelativePathName`) is allowed; after it one separator is skipped, as the client does, and the rest follows the same rules.
- **Address**: only `git@host:path` (scp-style SSH), `ssh://[user@]host[:port]/path` and `https://[userinfo@]host[:port]/path`, with no whitespace or control characters. The host and the ssh user start with a letter or digit, so ssh cannot take them for an option. Addresses starting with `-` (git options), `file://`, `ext::`, `http://` and local paths are refused.

### Authentication (API key)

- `AddApiKeyIdentity` (WebSystemTools.ApiKeyIdentity) registers the only authentication scheme, `ApiKeyAuthentication` (`TokenAuthenticationHandler`), as `DefaultAuthenticateScheme`; with a single scheme the challenge uses it as well and answers 401 (set `DefaultChallengeScheme` if a second scheme is ever added). `UseApiKeysAuthorization` calls only `UseAuthorization`: `WebApplication` adds `UseAuthentication` itself, after routing and before the rest of the pipeline, because the authentication services are registered. `Host/ApiKeyAuthenticationTests` proves both on the real host.
- The handler takes the `ApiKey` query parameter (case-insensitive; the CLI's `SystemTools.ApiContracts.ApiClient` sends `?apikey=<escaped key>`) and the client address (`RemoteIpAddress.MapToIPv4()`), and `ApiKeyByConfigFinder` looks them up in the configuration on every request: `ApiKeys:AppSettingsByApiKey: [{ ApiKey, RemoteIpAddress }]` (`SystemTools.ApiKeysManagement`, `ApiKeysDomain`). The key and the address must match exactly; an entry whose `RemoteIpAddress` is `*` accepts its key from any address, and an entry for the exact address wins over it. A refused key is logged only as the client address and the key length; a configured key never reaches a log.
- **Every route group is created with `.RequireAuthorization()`**: the three `api/v1/git` groups and the SignalR hub (`api/v1/messages`) are; only `api/v1/test/...` stays anonymous, because the VersionChecker calls it without a key. `OnlyTheTestRoutes_AreAnonymous` fails when a new route is anonymous.
- Real keys never go into `appsettings.json`: it holds one placeholder entry, whose address matches no client. Development: the User Secrets of the host (`ApiKeys:AppSettingsByApiKey:0:ApiKey` and `:0:RemoteIpAddress`, `*` for a key that works from any address); production: as task D1 of `docs/CentralRegistry` decides. The CLI sends the `ApiKey` of `ApiClients[SupportToolsServerWebApiClientName]`.
- Swagger (Development only) declares the `ApiKey` query parameter (`AddSwagger(debugLogger, ESwaggerSecurityScheme.ApiKey, ...)`), so its Authorize button adds the key to every call.

### Endpoints (`api/v1/git`, every group requires an API key)

Consumer: `SupportToolsServerApiClient` of the SupportTools CLI — the `Support Tools Server Editor` editors `LibSupportToolsServerWork/Cruders/*StsCruder.cs` (`GitStsCruder`, `GitIgnoreFileTypesStsCruder`, `EditorConfigFileTypesStsCruder`) and the sync commands `SupportTools/CliMenuCommands/SyncGitProjectsCliMenuCommand.cs`, `SupportTools/CliMenuCommands/GitIgnoreFileTypes/SyncGitignoreFilesCliMenuCommand.cs` and `SupportTools/CliMenuCommands/SyncEditorConfigFilesCliMenuCommand.cs`, which show the differences and offer Merge Up / Sync Up / Merge Down / Sync Down. A route with a key has a `…Prefix` constant in `SupportToolsServerApiRoutes`; the client appends `/{Uri.EscapeDataString(key)}`, the server maps the full `…/{key}` template. Keys and names match case-insensitively, like the unique indexes.

- Git repos (`GitReposEndpoints`): `GET gitrepos` (ordered by name), `GET gitrepo/{key}` (404 `GitWithKeyNotFound`), `POST updategitrepo/{key}` (add or update; the route key wins over the body's `GitProjectName`), `DELETE deletegitrepo/{key}`, `POST uploadgitrepos` (`SyncGitRequest`: upserts gitignore types and repos by name in one transaction, never deletes).
- GitIgnore file types (`GitIgnoreFileTypesEndpoints`): `GET gitignorefiletypeslist`, `POST updategitignorefiletype/{key}` (the CLI sends only the name: adds the type with empty content when missing, leaves an existing one unchanged), `DELETE deletegitignorefiletype/{key}`, `POST syncupgitignorefiletypes/{merge?}` (`merge=false` also deletes the server rows that are missing from the upload).
- EditorConfig file types (`EditorConfigFileTypesEndpoints`): `GET editorconfigfiletypeslist`, `POST syncupeditorconfigfiletypes/{merge?}` (called by the CLI's `Sync .editorconfig files...`, and by its `EditorConfig File Types` server editor with `merge=true` and a single row to add or replace one template), `DELETE deleteeditorconfigfiletype/{key}` (404 `EditorConfigFileTypeWithNameNotFound`). Rows match by name and keep the server `Id` like the gitignore types (`StsEditorConfigFileTypeDataModel` has no `Id`); nothing references them, so deleting needs no usage check. `EditorConfigFileType.ContentMaxLength` is 65536, because the templates are far larger than `.gitignore` files (the `default` one is ~16000 characters).

`GitRepo` references its pattern by `GitIgnoreFileTypeId` (FK, `Restrict`), while the contract carries `GitIgnorePatternName`. The CLI's sync-up sends a new `Guid` for every row, so `SyncUp` and `UploadGitRepos` match gitignore rows **by name** and keep the server `Id`; the client's `Id` is ignored. Deleting a type that a repo uses — by route or by `merge=false` — is refused with 409 `GitIgnoreFileTypeIsInUse`, an unknown pattern name with `GitIgnoreFileTypeWithNameNotFound`, and an address that another repo has with 409 `GitAddressIsInUse` (addresses are unique because the CLI's `GitCruder` looks a remote repo up by address). Errors are ProblemDetails from `CustomResults.Problem`; `SystemTools.ApiContracts.ApiClient` reads a code-shaped `title` (no spaces) as the error code, `detail` as the description, the status as the type and the `errors` extension as the list, so the CLI can compare codes such as `GitWithKeyNotFound`.

## Conventions

- DI extension methods take `ILogger? debugLogger` and log `"{MethodName} Started"` / `"{MethodName} Finished"`. Follow this pattern for new registration and `Use...` methods.
- A new route group is created with `.RequireAuthorization()` (see Authentication); an anonymous route needs a reason and an update of `OnlyTheTestRoutes_AreAnonymous`.
- Many code comments are in Georgian. Keep the language of surrounding comments.
- New projects/repos must also be registered in `D:\1WorkSecurity\SupportTools\SupportTools.json`, which lives outside every repo: a `Gits` entry and the `GitProjectNames` of every project record that clones the repo (`SupportToolsServer`, `SupportToolsServerDbTools`).
