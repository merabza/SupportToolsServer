## Architecture

Clean Architecture / CQRS, the same layout as `AppGanmartebaGe`. Request flow:

endpoint (`SupportToolsServer.WebApi/Endpoints/V1/*Endpoints.cs`) → command/query → `ICommandHandler`/`IQueryHandler` (`SupportToolsServer.Application/<Area>/<UseCase>/`) → repository interface (`SupportToolsServerCore.Domain`) → EF implementation (`SupportToolsServer.Infrastructure/Repositories`) over `ISupportToolsServerDbContext` → the handler commits with `IUnitOfWork.SaveChangesAsync` → `Result` → `TypedResults` / `CustomResults.Problem`.

- `SupportToolsServer.Application` — one folder per use case (`GitRepos/UpdateGitRepo/`, `GitIgnoreFileTypes/SyncUp/`, …) holding the command/query, its handler and an optional `AbstractValidator`. `AddApplication(debugLogger, typeof(SupportToolsServer.Application.AssemblyReference))` scans this assembly and decorates the handlers with validation + logging, and `AddFluentValidation` (WebSystemTools.ValidationTools) registers the validators, so a new handler or validator needs no DI code. Only **command** handlers get the validation decorator. Validators use the error codes of `SupportToolsServerApiClientErrors` (Shared repo); shared rules live in `Validation/` (`RequiredWithMaxLength`, `UniqueValues`, the git folder and address rules of `GitRules`, the absolute Windows file path of `PathRules`) and the lengths come from the entity constants (`GitRepo.NameMaxLength`, …) that the EF configurations also use.
- `SupportToolsServer.Infrastructure` — EF repositories; a new repository needs an `AddScoped` in `DependencyInjection/SupportToolsServerRepositoriesDependencyInjection.cs` (`AddSupportToolsServerRepositories`), which also registers the clock of the handlers (`TryAddSingleton(TimeProvider.System)`; the authentication of the host registers it as well). `GitProjects/` holds the server-side git clone/pull (see below), registered by `AddSupportToolsServerGitProjects`.
- `SupportToolsServer.WebApi` — minimal-API endpoint groups exposing `Use...Endpoints` extension methods, aggregated in `UseSupportToolsServerApi`. Endpoints inject `ICommandHandler<TCommand>` directly. Routes come from `SupportToolsServerApiRoutes` in the Shared repo.
- `SupportToolsServer` (host) — `Program.cs` wires `AddSupportToolsServerDatabase` (DbPart: context, `ISupportToolsServerDbContext`, `IUnitOfWork`, `IDomainEventsDispatcher`), `AddApplication`, `AddFluentValidation`, `AddSupportToolsServerRepositories` and `AddSupportToolsServerGitProjects`.

Repositories read with `AsNoTracking` and stage changes with explicit `Add`/`Update`/`Delete`; the handler commits once. The one exception is the read for the update of an aggregate with child collections, which is tracked (`GetByNameForUpdate`, see Registry conventions). The two singletons have no key to read by: their repositories have `Get()` instead of `GetByName` (see Registry conventions, Singletons). The stored files have `GetInfos()` and `GetByPath` instead of `GetAll` and `GetByName` (see Registry conventions, Stored files). Gitignore and editorconfig types are updated by passing a new instance with the stored `Id` and the stored `Version + 1` to `Update`. A `GitRepo` is changed in place instead: the handlers call `GitRepo.Update(...)` on the loaded no-tracking instance, which increments its `Version` and raises `GitRepoUpdatedDomainEvent`, and pass that same instance to the repository's `Update` (a new repo comes from `GitRepo.Create`, which raises `GitRepoAddedDomainEvent`). Every `Update` relies on that one increment (see Registry conventions). Adding a table: entity (+ repository interface) in `SupportToolsServerCore.Domain`, a `DbSet` on both `ISupportToolsServerDbContext` and `SupportToolsServerDbContext`, a configuration in `SupportToolsServerDbPart.Db/Configurations`, then a migration in `SupportToolsServerDbTools`, generated where the Core and DbPart clones are current; a registry aggregate follows Registry conventions. Migrations: the squashed `20261006043006_Initial` holds every table up to B7 (the three git tables, `Environments`, the lookups, the resources, `Servers`, `GlobalSettings`, `ProjectCreatorSettings`, `ProjectTemplates`, `Projects` with its six child tables, `ServerInfos` and `ServerInfoAllowedTools`); B8 added `20261006085209_AddStoredFiles` (`StoredFiles`). The user squashes the migrations into a new `Initial` from time to time, when the dev database is recreated; a database created before a squash records older migration IDs, so `database update` would run the new `Initial` again there: register its ID in `__EFMigrationsHistory` instead, once the schema matches.

### Server-side git clone/pull

Saving an added or updated `GitRepo` (`updategitrepo`, `uploadgitrepos`) also clones or updates that repo on the server, under `{AppOptions:WorkFolder}\Gits\`. `SupportToolsServerDbContext.SaveChangesAsync` dispatches the tracked entities' domain events after saving, through `IDomainEventsDispatcher` (`SystemTools.SharedKernel`):

`GitRepoAddedDomainEvent` / `GitRepoUpdatedDomainEvent` → `GitRepoSavedDomainEventHandler` → `UpdateGitProjectCommand` → queue (`GitProjectUpdateQueue`, a single-reader channel) → `GitProjectUpdateBackgroundService`, which runs `UpdateGitProjectCommandHandler` in its own scope, one command at a time.

The handler clones the repo (first deleting a folder that was cloned from another address), discards local changes in an existing clone, or otherwise pulls when the remote has new commits. The request does not wait for git, and git failures are only logged. The folder is the folder name with both separators replaced by `.` (the client's cache rule, `GitFolderCountHelper`), so it is always a direct subfolder of `Gits`; a folder name with the `{SpaProjectFolderRelativePath}` prefix uses the git's name instead, like the client's `GitRepos.Create` with `useGitRecordNameForComplexGitProjectFolderName`. After the validator (see the rules below), `GitsWorkFolder` is the second line of defence: it checks with `Path.GetFullPath` that the result is a subfolder of `Gits` (not `Gits` itself), otherwise it returns `FolderIsOutsideGitsFolder` and the handler neither deletes nor clones. `GitClient` passes every argument separately through `ProcessStartInfo.ArgumentList`, never as one interpolated string, and clones with `git clone -- <address> <path>`. `AddApplication` finds the domain-event handler like the command handlers; `AddSupportToolsServerGitProjects` registers the rest (`AppOptions`, the queue, the hosted service, `IGitsWorkFolder`, `IGitClient`). `AppOptions:WorkFolder` is required: it is validated with `ValidateOnStart`, so the host does not start without it (`appsettings.json` holds the relative default `WorkFolder`).

### Git folder and address rules

`GitRepoModelValidator` (so both `updategitrepo` and `uploadgitrepos`) checks the two values with `Validation/GitRules`; the error codes are `InvalidGitFolderName` and `InvalidGitAddress` (Shared repo).

- **Folder name**: a relative path of one or more segments separated by `\` or `/`. A segment is not empty, contains none of `< > : " | ? *` and no control characters (a fixed set, not `Path.GetInvalidFileNameChars()`, so the result does not depend on the OS), and does not end with `.` or a space. That also rules out `.`, `..`, the names Windows trims to them (`...`, `.. `) and rooted paths (`C:`, `\\server`, `/x`). A leading `{SpaProjectFolderRelativePath}` (the client's `GitDataModel.SpaProjectFolderRelativePathName`) is allowed; after it one separator is skipped, as the client does, and the rest follows the same rules.
- **Address**: only `git@host:path` (scp-style SSH), `ssh://[user@]host[:port]/path` and `https://[userinfo@]host[:port]/path`, with no whitespace or control characters. The host and the ssh user start with a letter or digit, so ssh cannot take them for an option. Addresses starting with `-` (git options), `file://`, `ext::`, `http://` and local paths are refused.

### Authentication (API key)

- `AddApiKeyIdentity` (WebSystemTools.ApiKeyIdentity) registers the only authentication scheme, `ApiKeyAuthentication` (`TokenAuthenticationHandler`), as `DefaultAuthenticateScheme`; with a single scheme the challenge uses it as well and answers 401 (set `DefaultChallengeScheme` if a second scheme is ever added). `UseApiKeysAuthorization` calls only `UseAuthorization`: `WebApplication` adds `UseAuthentication` itself, after routing and before the rest of the pipeline, because the authentication services are registered. `Host/ApiKeyAuthenticationTests` proves both on the real host.
- The handler takes the `ApiKey` query parameter (case-insensitive; the CLI's `SystemTools.ApiContracts.ApiClient` sends `?apikey=<escaped key>`) and the client address (`RemoteIpAddress.MapToIPv4()`), and `ApiKeyByConfigFinder` looks them up in the configuration on every request: `ApiKeys:AppSettingsByApiKey: [{ ApiKey, RemoteIpAddress }]` (`SystemTools.ApiKeysManagement`, `ApiKeysDomain`). The key and the address must match exactly; an entry whose `RemoteIpAddress` is `*` accepts its key from any address, and an entry for the exact address wins over it. A refused key is logged only as the client address and the key length; a configured key never reaches a log.
- The request log of ASP.NET Core (`Microsoft.AspNetCore.Hosting.Diagnostics`, "Request starting/finished") writes the whole address, query included, for the REST calls (`?apikey=`) and the message hub (`?ApiKey=…&id=…`) alike. `UseSerilogLogger` (WebSystemTools) therefore adds `ApiKeyRedactionEnricher` in code, whatever the configuration says: it replaces the value of the `ApiKey` query parameter (any case) with `***` in every text of a log event, nested ones too, and keeps the other parameters. It cannot change message templates or exception texts, so never put an address into a log message by string interpolation. `Host/RequestLogTests` proves it on the real host. The client side needs nothing: the `IHttpClientFactory` log of .NET 10 writes `?*` instead of the query, and `ApiClient` masks the key in its own messages.
- **Every route group is created with `.RequireAuthorization()`**: the three `api/v1/git` groups, the registry groups (`api/v1/environments`, …) and the SignalR hub (`api/v1/messages`) are; only `api/v1/test/...` stays anonymous, because the VersionChecker calls it without a key. `OnlyTheTestRoutes_AreAnonymous` fails when a new route is anonymous.
- Real keys never go into `appsettings.json`: it holds one placeholder entry, whose address matches no client. Development: the User Secrets of the host (`ApiKeys:AppSettingsByApiKey:0:ApiKey` and `:0:RemoteIpAddress`, `*` for a key that works from any address); production: as task D1 of `docs/CentralRegistry` decides. The CLI sends the `ApiKey` of `ApiClients[SupportToolsServerWebApiClientName]`.
- Swagger (Development only) declares the `ApiKey` query parameter (`AddSwagger(debugLogger, ESwaggerSecurityScheme.ApiKey, ...)`), so its Authorize button adds the key to every call.

### Endpoints (`api/v1/git`, every group requires an API key)

Consumer: `SupportToolsServerApiClient` of the SupportTools CLI — the `Support Tools Server Editor` editors `LibSupportToolsServerWork/Cruders/*StsCruder.cs` (`GitStsCruder`, `GitIgnoreFileTypesStsCruder`, `EditorConfigFileTypesStsCruder`) and the sync commands `SupportTools/CliMenuCommands/SyncGitProjectsCliMenuCommand.cs`, `SupportTools/CliMenuCommands/GitIgnoreFileTypes/SyncGitignoreFilesCliMenuCommand.cs` and `SupportTools/CliMenuCommands/SyncEditorConfigFilesCliMenuCommand.cs`, which show the differences and offer Merge Up / Sync Up / Merge Down / Sync Down. A route with a key has a `…Prefix` constant in `SupportToolsServerApiRoutes`; the client appends `/{Uri.EscapeDataString(key)}`, the server maps the full `…/{key}` template. Keys and names match case-insensitively, like the unique indexes. The GETs also return each record's `Version`; the POSTs ignore it, because the CLI's editors and sync commands send none (see Registry conventions).

- Git repos (`GitReposEndpoints`): `GET gitrepos` (ordered by name), `GET gitrepo/{key}` (404 `GitWithKeyNotFound`), `POST updategitrepo/{key}` (add or update; the route key wins over the body's `GitProjectName`), `DELETE deletegitrepo/{key}` (409 `RecordIsInUse` while a project uses the git), `POST uploadgitrepos` (`SyncGitRequest`: upserts gitignore types and repos by name in one transaction, never deletes).
- GitIgnore file types (`GitIgnoreFileTypesEndpoints`): `GET gitignorefiletypeslist`, `POST updategitignorefiletype/{key}` (the CLI sends only the name: adds the type with empty content when missing, leaves an existing one unchanged), `DELETE deletegitignorefiletype/{key}`, `POST syncupgitignorefiletypes/{merge?}` (`merge=false` also deletes the server rows that are missing from the upload).
- EditorConfig file types (`EditorConfigFileTypesEndpoints`): `GET editorconfigfiletypeslist`, `POST syncupeditorconfigfiletypes/{merge?}` (called by the CLI's `Sync .editorconfig files...`, and by its `EditorConfig File Types` server editor with `merge=true` and a single row to add or replace one template), `DELETE deleteeditorconfigfiletype/{key}` (404 `EditorConfigFileTypeWithNameNotFound`). Rows match by name and keep the server `Id` like the gitignore types (`StsEditorConfigFileTypeDataModel` has no `Id`). Projects reference a template by `EditorConfigFileTypeId` (FK, `Restrict`, contract `EditorConfigPatternName`), so deleting one that a project uses — by route or by `merge=false` — is refused with 409 `RecordIsInUse` (`EditorConfigFileTypeDeletion`: one error for every such template, in name order, each with its projects). `EditorConfigFileType.ContentMaxLength` is 65536, because the templates are far larger than `.gitignore` files (the `default` one is ~16000 characters).

`GitRepo` references its pattern by `GitIgnoreFileTypeId` (FK, `Restrict`), while the contract carries `GitIgnorePatternName`. The CLI's sync-up sends a new `Guid` for every row, so `SyncUp` and `UploadGitRepos` match gitignore rows **by name** and keep the server `Id`; the client's `Id` is ignored. Deleting a type that a repo uses — by route or by `merge=false` — is refused with 409 `GitIgnoreFileTypeIsInUse`, an unknown pattern name with `GitIgnoreFileTypeWithNameNotFound`, and an address that another repo has with 409 `GitAddressIsInUse` (addresses are unique because the CLI's `GitCruder` looks a remote repo up by address). Errors are ProblemDetails from `CustomResults.Problem`; `SystemTools.ApiContracts.ApiClient` reads a code-shaped `title` (no spaces) as the error code, `detail` as the description, the status as the type and the `errors` extension as the list, so the CLI can compare codes such as `GitWithKeyNotFound`.

  - The server does not know the enums of the client: `PeriodType`, `DatabaseServerProvider`, `SupportProjectType`, `ProjectType`, `DatabaseRecoveryModel`, `BackupType`, `HttpMethod`, `EndpointType` and the tool names are checked only for their length.
  - Nothing references DotnetTool, ProjectTemplate (the client's projects keep no template name), Project or StoredFile, so their deletes have no usage check.
- **Singletons** (B5's `GlobalSettings`, the shared fields of the client's `SupportToolsParameters`, and `ProjectCreatorSettings`, its `AppProjectCreatorAllParameters` without `Templates`): one record per table, without a name.
  - The key: the typed Guid id of every aggregate, but fixed: `GlobalSettingsId.Singleton` and `ProjectCreatorSettingsId.Singleton` (`00000000-0000-0000-0000-000000000001`), which `Create` always uses. The configuration adds `CK_<Table>_Singleton` (`[Id] = '…0001'`), so the database refuses any other key. When two first creates run at once, the second INSERT fails on the primary key and `RecordVersions.SaveChanges` returns 409 `ConcurrencyConflict`, as the unique name index does for the collections; a random key would leave two rows.
  - Repository: `Get()` reads the only row without tracking (the CHECK makes a filter unnecessary), plus `Add` and `Update`; there is no delete.
  - Routes: `SupportToolsServerApiRoutes.GlobalSettings` and `.ProjectCreatorSettings` hold `Base` (`/settings/global`, `/settings/projectcreator`), `Get = ""` and `Update = "/update"`; there is no key and no DELETE.
    - `GET settings/global` returns the contract, or **an empty contract with `Version = 0`** before the first create, not 404. The sync adapter (C3) reads `Version == 0` as "no server record" without an error path. A 404 would be an error to tell from real failures (the sync engine stops the plan on any read failure), and the SystemTools `ApiClient`, which SupportTools creates with the console, would print it on every sync until the first upload.
    - `POST settings/global/update` is the upsert of Routes with the body's `Version`: 0 creates (409 when the record exists), N updates, a missing record with N ≠ 0 is 404 `RecordWithNameNotFound`.
    - Nothing can delete a singleton. The SupportTools sync adapter (C3, `SingletonRegistrySyncAdapter`) therefore counts an empty contract as no record on both sides (the user's choice), so a new computer pulls the singleton without a FirstSyncDiffers conflict. Its delete is this upsert with an empty contract and the expected version, and a later create over such an emptied row sends the row's version instead of 0.
  - Errors: entityName `Settings` and the fixed names `Global` and `ProjectCreator` (`<X>ContractMapper.EntityName` and `RecordName`), e.g. `Settings Global Version Conflict: Expected 0, Actual 1`.
  - Users: a singleton has no name, so the 409 of a referenced record names the field, as the contract calls it: `GlobalSettings.FileStorageNameForExchange`, `GlobalSettings.DatabasesBackupFilesExchange.ExchangeFileStorageName`, `ProjectCreatorSettings.ProductionServerName`. The mappers' `GetUsages(<referenced id>)` overloads give them in the order of the contract (`Registry/ReferenceFields.Usages`), none before the first create.
  - `GlobalSettings.DatabasesBackupFilesExchange` (the client's `DatabasesBackupFilesExchangeParameters` without the machine's `LocalPath`) is an EF owned type in the same row: `OwnsOne`, columns `DatabasesBackupFilesExchange_<Field>`, its own FKs to FileStorages and SmartSchemas. The navigation is required, so a part whose columns are all NULL is read as an empty part, not as null. EF cannot pass an owned type to a constructor, so `GlobalSettings` has a private constructor without it, which EF uses. The contract nests the part (`StsDatabasesBackupFilesExchangeDataModel`); the validator refuses a null part (`ValueRequired`) and names its fields `DatabasesBackupFilesExchange.<Field>`.
- **Stored files** (B8's `StoredFile`, table `StoredFiles`, route `files`; README G2, §4.1): the text files that the registry points to (`ServerInfo.AppSettingsJsonSourceFileName`, …), in plain text, which the client's C6 syncs.
  - Fields: `Path` 400 (the canonical path, README G3, and the key: unique, matched `OrdinalIgnoreCase`; above MAX_PATH for long paths, below 450 so that the key of the unique index fits the 900 bytes of SQL Server), `Content` (nvarchar(max), secret), `Sha256` 64 (upper case hex of the SHA-256 of the UTF-8 bytes of the content, without BOM) and `Length` (the count of those bytes), both computed by `StoredFile.Create`/`Update`, `UpdatedAtUtc` (from the `TimeProvider` of the handler; `datetime` by `DatabaseEntitiesDefaultConvention`, and the configuration marks the read value as UTC, so the JSON ends with `Z`) and `Version`.
  - Validation (`StoredFileModelValidator`): the path by `Validation/PathRules`, otherwise 400 `InvalidFilePath`: `X:\` and one or more segments separated by `\`; a segment is not empty, holds none of `< > : " / | ? *` and no control characters, and does not end with `.` or a space (so no `.` or `..`); UNC, `\\?\`, relative paths and `/` are refused. The content may be empty but not null and has at most `StsStoredFileDataModel.ContentMaxBytes` (1 MiB) UTF-8 bytes, otherwise 400 `ValueTooLarge` (bytes, the unit of `Sha256` and `Length`: the user's B8 choice; the largest real file had 42 KB). The messages name the path, never the content.
  - Routes (`SupportToolsServerApiRoutes.StoredFiles`): the path cannot be a route key (`\`, `:`). `GET files` returns the metadata (`StsStoredFileInfoDataModel`: `Path`, `Sha256`, `Length`, `UpdatedAtUtc`, `Version`) ordered by path, `GET files/content?path=…` one file (`StsStoredFileDataModel`: `Path`, `Content`, `Version`), `POST files/update` is the upsert of Routes with the body's path as the key (changing only its case is an update), `DELETE files/delete?path=…&version=N` deletes like Routes, without a usage check. The client escapes the path with `Uri.EscapeDataString`; ASP.NET Core unescapes a query value fully, so there is no `RouteKeys`.
  - Repository (`IStoredFileRepository`, no `ICrudRepository`): `GetInfos` projects the metadata without the content column, `GetByPath` reads `Id` and `Path` first and then only the file found; plus `Add`, `Update` and `Delete`.
  - Errors: entityName `StoredFile`, with the path as the name (`StoredFile With Name D:\… Not Found`).
- **Optional owned parts** (B6's `DatabaseParameters`, reused by B7 for the ServerInfo's `CurrentDatabaseParameters` and `NewDatabaseParameters`, in the `ServerInfos` row): an EF owned type in the owner's row (table splitting, not a table of its own: EF cannot put two owned navigations of one type into one table), configured by the shared `DatabaseParametersConfiguration.Configure` (columns `<Navigation>_<Field>`, its own `Restrict` FKs).
  - Unlike `GlobalSettings.DatabasesBackupFilesExchange`, the navigation is **not** required: null means that the project has no such parameters, and the client checks that (`project.DevDatabaseParameters == null`). EF tells a missing part from an empty one by its required fields (`CommandTimeOut`, `SkipBackupBeforeRestore`), whose columns are nullable: they are NULL only when the part is missing.
  - The update replaces the part through the tracked read of the aggregate: EF writes the new values, or NULLs for a removed part, into the same `UPDATE … WHERE Version`.
  - The contract nests `StsDatabaseParametersDataModel?`. `DatabaseParametersModelValidator` names the fields `<Part>.<Field>` (`DevDatabaseParameters.DatabaseName`, `ServerInfos.PAZISI|Prod.CurrentDatabaseParameters.DatabaseName`): the owner passes the part name through its internal constructor (the ServerInfo validator per instance, through `SetValidator(x => …)`), the public parameterless one is for `AddFluentValidation`. `DatabaseParametersContractMapper` maps both ways (`ToContractModel`, and `FindDatabaseParameters`, which resolves the three references through `ReferencedRecords`).
- **Aggregates with child collections** (B3's SmartSchema and DatabaseServerConnection, B6's Project with B7's ServerInfos):
  - Domain: the root keeps its children in a private list exposed as `IReadOnlyList`; `Create` and `Update` take the whole child list, and `Update` replaces it (README G7) and increments the root's `Version`. A child derives from `Entity<TId>` with its own typed Guid id and has no version.
  - EF: the child has its own configuration with `ToTable("<plural>")` (it has no `DbSet`), a shadow foreign key to the root, `HasOne<Root>().WithMany(x => x.Children).HasForeignKey("<Root>Id").IsRequired().OnDelete(DeleteBehavior.Cascade)`, and a unique index on (root id, the child's key). The relationship must be required: an optional one would leave the replaced children as orphans with a NULL key instead of deleting them.
  - Repository: `GetAll` and `GetByName` read without tracking, with `Include`. `GetByNameForUpdate` finds the id by name (a no-tracking `Id`/`Name` projection compared with `OrdinalIgnoreCase`) and loads only that aggregate **tracked**, so that `SaveChanges` deletes the replaced children (before inserting a new child with the same key) and inserts the new ones, in the same transaction as the root's `UPDATE … WHERE Version`. `Update` stays `Update(entity).ExpectPreviousVersion()`; EF keeps the states of the tracked children. `Delete` takes the no-tracking read; EF deletes the loaded children and the database cascade covers the rest.
  - Handler: the update handler reads with `GetByNameForUpdate`, but `RecordVersions.SaveChanges` reads the version again with `GetByName`, because a tracking query would return this request's changed instance instead of the stored version.
  - Contract: the children are a list sorted by their key (`OrdinalIgnoreCase`), so the client's hash is stable. The validator refuses a null list (`ValueRequired`), a child without key or with a longer key, and a repeated key (`ValuesNotUnique`, ignoring case). A child validator is public and parameterless, because `AddFluentValidation` registers every public validator in DI; so its messages name the list (`Details.PeriodType`, `DatabaseFoldersSets.<name>.Backup`) and not the root.
  - The Project (B6) has seven child collections and two owned parts; the seventh, B7's ServerInfos, has a child collection (`ServerInfoAllowedTools`) and two owned parts of its own:
    - **Full replacement** (README G7): `Project.Update` replaces every scalar, both owned parts and all seven lists at once, and the version grows on every update, also when only a child or a ServerInfo changed. There is no partial update. On the tracked read EF deletes the replaced ServerInfos with their tools (the old row of a kept server/environment pair before the new one is inserted) and inserts the new ones, in the same transaction.
    - Repository: one `Include` per collection with `AsSplitQuery`, the ServerInfos with `ThenInclude(x => x.AllowedTools)` (nine queries instead of one cartesian JOIN); `GetByName` and `GetByNameForUpdate` find the id through the `Id`/`Name` projection first. `GET projects` returns the full aggregates (61 projects, 42 ServerInfos).
    - **Sorted lists**: the contract carries the set-like lists as names sorted `OrdinalIgnoreCase` (`GitProjectNames`, `ScaffoldSeederGitProjectNames`, `FrontNpmPackageNames`, `RedundantFileNames`, `AllowToolsList` of the project and of every ServerInfo), the client's dictionaries as records sorted by `Name` (`Endpoints`, `RouteClasses`) and the ServerInfos by `ServerName`, then `EnvironmentName`, so the client's hash does not depend on the order. The validator refuses a null list, a null record, a blank or longer item and a repeated item or key (ignoring case).
- **References to another aggregate** (B3's `DbWebAgentName`, B4's three references of `Server`, B5's settings and `ProjectTemplate.ReactTemplateName`, B6's projects and B7's ServerInfos):
  - The entity holds the typed id (a nullable FK, `Restrict`), the contract the name. The update handler resolves the name with `GetByName` of the other repository, after the version check: a null or blank name is no reference, a missing name is 404 `ReferencedRecordsNotFound(<the referenced EntityName>, [names])`. The GETs map ids to names with `ToNamesById` over the other repository's `GetAll` (`Registry/ReferenceFields.GetName` for a nullable id).
  - With several references the handler resolves all of them first and returns every missing name in one 404, grouped by the referenced type in the order of the contract, each name once: `Registry/ReferencedRecords` (`Find` per reference, then `AreAllFound` and `MissingError()`, which uses `ReferencedRecordsNotFound(ILookup<string, string>)`, see Errors).
  - A list of references (the gits and the npm packages of a project, the servers, environments and web agents of its ServerInfos) reads the other aggregate once with `GetAll` and matches the names `OrdinalIgnoreCase` in memory, through the synchronous `ReferencedRecords.Find(name, entityName, findByName)`; a project without such names reads nothing. The database parameters of the ServerInfos use `FindDatabaseParameters` like the project's own; their missing names join the groups of the project's (the ServerInfos come last in the contract).
  - The delete handler of the referenced area collects the users as `"<EntityName> <Name>"`, type after type, each type in name order (a singleton by its field, see Singletons), and refuses with 409 `RecordIsInUse`. `DeleteApiClientCommandHandler.GetUsages`: the DatabaseServerConnections, then the Servers that use it as either web agent (a server once), then the field of GlobalSettings, then the ServerInfos that use it as `WebAgentNameForCheck`; `DeleteRuntimeCommandHandler.GetUsages`: the Servers; `DeleteReactAppTemplateCommandHandler.GetUsages`: the ProjectTemplates; the deletes of FileStorage and SmartSchema: the fields of GlobalSettings, then those of ProjectCreatorSettings, then the Projects with their ServerInfos; the deletes of Server and Environment: the field of ProjectCreatorSettings, then the ServerInfos; the delete of DatabaseServerConnection: the field of ProjectCreatorSettings, then the Projects with their ServerInfos; the deletes of GitRepo (the old `deletegitrepo`), NpmPackage and EditorConfigFileType (and the editorconfig SyncUp with `merge=false`): the Projects. A project is listed once as `Project <Name>`, whichever of its own fields or children uses the record; each ServerInfo that uses it is listed after its project as `Project <Name> / <Server>|<Env>` (the user's B7 choice), the projects in name order and the ServerInfos of a project by server and environment (`ProjectContractMapper.GetUsages(<referenced id>[, ServerInfoKeyNames])`; `ServerInfoKeyNames` reads the names of the servers and environments).
  - A reference deleted between the check and the save fails the FK; `RecordVersions.SaveChanges` maps only version races, so that propagates as 500.
- **Secrets** (README G2: ApiKey, the passwords, the user names, `MediatRLicenseKey`, the projects' `KeyGuidPart` and the content of the stored files): stored in plain text, but never in a `Debug.WriteLine` trace (the traces name the record only, a stored file by its path), a log, an error text or a validation message (the messages name the field, never its value). The client's update methods whose body holds a secret (`UpdateFileStorage`, `UpdateApiClient`, `UpdateDatabaseServerConnection`, `UpdateGlobalSettings`, `UpdateProject`, `UpdateStoredFile`) call `PostAsyncReturn<T>(…, bodyContainsSecrets: true, …)` of the SystemTools `ApiClient`, which keeps the body off the console when the server answers with an error; SupportTools creates its client with the console. A new client method that sends a secret does the same.
- **Version (optimistic concurrency)**:
  - Every aggregate root derives from `Primitives/VersionedEntity<TId>` (`int Version`, `protected IncrementVersion()`). A new record gets `EntityVersion.Initial` (1). The domain `Update(...)` method calls `IncrementVersion()`. The types that only have a constructor (`GitIgnoreFileType`, `EditorConfigFileType`) get the stored `Version + 1` from the handler. Child entities of an aggregate have no version of their own (README G7).
  - EF: every configuration has `Property(x => x.Version).IsConcurrencyToken().HasDefaultValue(EntityVersion.Initial)`. The default gives version 1 to existing rows when the column is added. `SupportToolsServerDbContextTests` (DbPart) checks this for every `VersionedEntity` of the model.
  - Repository `Update` is `_dbContext.X.Update(entity).ExpectPreviousVersion()` (`Repositories/VersionedEntityEntryExtensions`). `DbSet.Update` takes the current values as the originals. Records are read with `AsNoTracking`, and between the read and `Update` the version grows exactly once, so the original of the token is `Version - 1`: `UPDATE … WHERE Id = @Id AND Version = <read>`. `Delete` removes the read instance: `DELETE … WHERE Version = <read>`. When another request saves the record in between, `SaveChanges` throws `DbUpdateConcurrencyException` and nothing is written.
  - Handlers check the expected version with `Registry/RecordVersions.Check` and save with `RecordVersions.SaveChanges`. On a `DbUpdateException` (the token, or the unique name index when two requests create the same name), `SaveChanges` reads the stored version again and repeats the check, returning its 409 or 404. If the check still passes, the exception propagates (500).
  - The old git endpoints return `Version` from their GETs and ignore it in their POSTs (the CLI sends none, which reads as 0). `UpdateGitRepo` and `UploadGitRepos` increment the version of every git they update. Both SyncUps increment it on every type they rewrite, changed or not. `EnsureGitIgnoreFileType` creates version 1. They don't map the race to 409: two concurrent writes now fail with 500 instead of silently overwriting each other.
- **Routes**: `SupportToolsServerApiRoutes.<Area>` holds `Base = "/<area>"`, `List = ""`, `ByKey = "/{key}"`, `UpdatePrefix = "/update"` + `Update`, and `DeletePrefix = "/delete"` + `Delete`. The group is `MapGroup(ApiBase + <Area>.Base).RequireAuthorization()`. The singletons have a shape of their own (see Singletons).
  - `GET <area>`: every record with all its fields and `Version`, ordered by name (`OrdinalIgnoreCase`).
  - `GET <area>/{key}`: one record, or 404 `RecordWithNameNotFound`.
  - `POST <area>/update/{key}`: upsert. The body is the contract, and its `Version` is the expected version:
    - 0 creates; 409 `ConcurrencyConflict` if the name exists;
    - N updates only when N is stored, otherwise 409 `ConcurrencyConflict` with the actual version;
    - a missing record with N ≠ 0 is 404 `RecordWithNameNotFound` (deleted on the server);
    - the route key wins over the body's name, so changing the case of a name is an update;
    - the response is `Ok<int>`, the new version; the client returns it as `Result<int>`, as the sync engine's `IRegistrySyncAdapter.Upsert` expects.
  - `DELETE <area>/delete/{key}?version=N`: 404 when missing, 409 `ConcurrencyConflict` when N is not the stored version, 409 `RecordIsInUse` with the list of users when another aggregate references the record (FKs to another aggregate are `Restrict`, README §4.2). Without `version` the delete is unconditional (manual editors). The usage check goes where the area's delete handler marks it (`DeleteEnvironmentCommandHandler`, `DeleteRuntimeCommandHandler`, …).
  - The key: the client escapes it with `Uri.EscapeDataString`. ASP.NET Core unescapes a route value except `%2F`, so the endpoints pass the key through `RouteKeys.Decode` (WebApi) to get the `/` of names such as npm's `@scope/name` back (`Host/RouteKeyTests`). The old git endpoints don't decode.
  - The client's GET and POST registry methods pass `useMessageHubClient: false`. The SystemTools `ApiClient.DeleteAsync` has no such flag, so a delete always runs the message hub.
- **Errors** (`SupportToolsServerApiClientErrors`): generic factories with a readable entity name such as `Environment` (`<Area>ContractMapper.EntityName`) instead of per-entity codes:
  - `RecordWithNameNotFound(entityName, name)` 404;
  - `RecordIsInUse(entityName, name, usages)` 409; the overload `RecordIsInUse(entityName, ILookup<string, string>)` (the users by record name) is one error for several records of one type (the editorconfig SyncUp), their texts joined with `; `; for one record it equals the first factory;
  - `ConcurrencyConflict(entityName, name, expectedVersion, actualVersion)` 409;
  - `ReferencedRecordsNotFound(entityName, names)` 404, when a contract names a missing record of another aggregate (`DatabaseServerConnection.DbWebAgentName`); `entityName` is the referenced aggregate (`ApiClient`). The overload `ReferencedRecordsNotFound(ILookup<string, string>)` (the names by `entityName`) is one error for several referenced types, their texts joined with `; ` (`Referenced ApiClient Records Not Found: A, B; Referenced Runtime Records Not Found: C`); for one type it equals the first factory.

  The sync engine of SupportTools matches `ConcurrencyConflict` and `RecordWithNameNotFound` by literal code (`RegistrySyncServerErrorCodes`), so never rename them. Field rules use `RequiredWithMaxLength` and `OptionalWithMaxLength` (`Validation/TextRules`); a number out of its range is 400 `ValueOutOfRange(valueName, minValue, maxValue)` (B7's `ServerSidePort`), a value larger than its size in bytes 400 `ValueTooLarge(valueName, maxBytes)` and a path that is not an absolute Windows file path 400 `InvalidFilePath(valueName)` (B8's stored files); a negative `Version` needs no rule, because it never matches.
- **Names** match case-insensitively (README G8). `GetByName` compares with `OrdinalIgnoreCase` in memory, independent of the database collation: SQLite's unique index is case-sensitive, SQL Server's default collation is not, and the registry tables are small. A large aggregate selects `Id` and `Name` first and loads the aggregate by id (`ProjectRepository`). The unique index on the name stays as the database-side guard.

## Conventions

- DI extension methods take `ILogger? debugLogger` and log `"{MethodName} Started"` / `"{MethodName} Finished"`. Follow this pattern for new registration and `Use...` methods.
- A new route group is created with `.RequireAuthorization()` (see Authentication); an anonymous route needs a reason and an update of `OnlyTheTestRoutes_AreAnonymous`.
- A new shared collection follows Registry conventions, with Environments as the template.
- Many code comments are in Georgian. Keep the language of surrounding comments.
- New projects/repos must also be registered in `D:\1WorkSecurity\SupportTools\SupportTools.json`, which lives outside every repo: a `Gits` entry and the `GitProjectNames` of every project record that clones the repo (`SupportToolsServer`, `SupportToolsServerDbTools`).
